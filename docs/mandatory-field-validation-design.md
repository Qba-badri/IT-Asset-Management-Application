Status: **P1–P3 implemented** (foundation, schema, pilot). P4–P5 not started.

Decisions taken: rules sourced from existing NestJS DTOs (single source of truth); design first, implement after review.

## 2. What the survey found

Five findings that shape the design. The first is a live bug.

**2.1 — A conditional-required rule is dead code.** `frontend/src/hooks/useForm.ts:35-59` only runs the `custom` validator inside `if (value)`. But `frontend/src/features/Assets/AssetManagement.tsx:151` is written as `(val, all) => (all.targetType === 'PERSON' && !val) ? 'User is required…' : null` — it can only return its error when `val` is truthy, so the `!val` branch is unreachable. **That check has never fired.** Any conditional-required rule written against `custom` today is silently inert. This alone justifies the work.

**2.2 — The backend is permissive, and required-ness lives in the UI.** Across 17 DTOs: `@IsOptional` appears **223** times, `@IsNotEmpty` **18**. So AC1's server half is largely *not currently true* — today the UI is the only thing stopping most bad records. This is the single biggest scope driver: sourcing rules from DTOs means the DTOs must first be made to actually state the rules.

**2.3 — 400s are surfaced wrong everywhere.** NestJS returns `message` as a **string array** for validation failures. Every call site does `showToast(error.response?.data?.message || 'Failed to save')` (e.g. `CategoryMaster.tsx:96`, `UserManagement.tsx:269`) — so a validation 400 renders as a comma-joined blob and field errors never reach the fields. `services/apiClient.ts` intercepts only 401.

**2.4 — `react-hook-form@7.71.1` is installed and never imported.** A dead dependency. Meanwhile there are two hand-rolled tiers: the custom `useForm` + shared `FormField` (6 files), and ad-hoc `useState`+`validate()` (~8 files). `LicenseForm.tsx:38-56` even redefines its own local `FormField` with its own asterisk, duplicating `components/shared/FormField.tsx:39`.

**2.5 — Two of the requirements have no surface to build on.** There is **no copy/duplicate feature anywhere** in the app, and bulk operations exist **only** for users (`UserManagement.tsx:254-271` → `/users/bulk-status`, `/users/bulk-delete`). Requirement 7 is therefore partly hypothetical — see Assumptions.

Also: **no i18n library is installed** and every string is hardcoded, including all validation messages.

## 3. Design

### 3.1 Single source of truth

DTO decorators are the source. Rules are authored **once**, in the DTO, and the frontend consumes them — it never re-declares them.

```
backend/src/modules/*/dto/*.ts   ← author rules here (class-validator)
        │
        │  reflect metadata at boot
        ▼
GET /schema/:formKey  →  { fields: [{ name, type, required, rules, conditions }] }
        │
        ▼
frontend  useValidatedForm(schema)  →  FormField renders * , blocks submit
```

The schema endpoint is generated by reading class-validator's metadata storage (`getMetadataStorage().getTargetValidationMetadatas(...)`), so it cannot drift from the DTO — that's AC5. Served cached at boot; it's static per deploy.

### 3.2 The five components

1. **`ValidationSchemaService`** (backend, new) — reflects DTO metadata into a serializable schema. Registry maps `formKey → DTO class`.
2. **`ValidationExceptionFilter`** (backend, new) — there is **no exception filter in the codebase today**. Reshapes Nest's `{ message: string[] }` into `{ errors: { field: message[] } }`. Logs failures with correlation id (req 12).
3. **`messages.ts`** (shared, new) — the message catalog. Keys, not sentences, at every call site.
4. **`useValidatedForm`** (frontend, new) — wraps **react-hook-form** (already a dependency — activate it rather than extend the buggy custom hook) with the fetched schema. Exposes the same surface as today's `useForm` so migration is mechanical.
5. **`FormField`** (frontend, **extend the existing** `components/shared/FormField.tsx`) — already does asterisk + `aria-required` + `aria-invalid` at line 39/61-70. Keep it; add the field-type matrix.

### 3.3 Conditional rules

`@ValidateIf` is the backend mechanism (already used correctly at `inventory-mgmt.dto.ts:97-103`). Its predicate is a JS closure and **cannot be serialized to the client**. So conditional rules get a declarative wrapper:

```ts
@RequiredWhen('targetType', 'PERSON')   // new decorator; emits @ValidateIf + serializable metadata
userId?: string;
```

This is the crux of the design: it's the only way one authored rule can enforce on both sides. The three existing conditional rules migrate to it — including the LOCATION branch that the frontend is currently **missing entirely** (`AssetManagement.tsx` mirrors only the PERSON half of the backend rule).

Rules too complex for the wrapper (e.g. `LicenseForm.tsx:232-236`, expiry-after-purchase) stay as explicit cross-field validators registered by key on both sides. Not everything should be declarative.

**Rules are not configurable per role or per tenant.**
- *Tenant*: the app **is not multi-tenant**. Every `tenant` reference is either the Azure AD tenant id for the sync integration or `license.entity.ts:58` `tenant_id` ("AWS Account ID, Azure Tenant ID") — a cloud-provider field on a license, not app tenancy.
- *Role*: rejected deliberately. It breaks the single-source-of-truth property the design rests on — a DTO cannot express "required unless Admin" without reintroducing the closure-serialization problem `@RequiredWhen` exists to avoid — and it multiplies the test matrix by the role count. If a real case appears, model it as a **separate DTO with its own `formKey`**, keeping rules static per form.
- Note: the existing permission-tier scoping (`common/dashboard-scope.ts`, global/department/self) governs **data visibility**, not field rules. Do not conflate the two.

### 3.5 Client schema caching & staleness

The schema is static per deploy (reflected at boot), so:

- **Cache in memory**, module-level `Map` keyed by `formKey`, fetched once per session. **Not `localStorage`** — a schema surviving across a deploy is precisely the staleness failure mode.
- The endpoint returns the **build id**; the client refetches when its build id no longer matches.
- **On fetch failure, submit anyway** and let the server validate. A form must never be unusable because a schema call failed.

**When the client schema is stale, the server wins — by design.** The client schema is a UX optimization; the server is the enforcement boundary. On disagreement the submit passes client-side, the server 400s, and the P1 error mapping lands the messages on the correct fields. The user gets a correct experience, one round-trip later — graceful degradation, not a bug.

This is exactly why **P1 (error mapping) ships before P2 (schema)**: the fallback path must work before anything depends on it.

### 3.4 Field types

`FormField` gets one emptiness predicate per type — this is where "required" actually means different things:

| Type | Empty when | Note |
|---|---|---|
| Text | `''` after trim | |
| Number | `null`/`undefined`/`NaN` | **`0` is valid** — the classic bug |
| Date | null or unparseable | |
| Dropdown | `''` or sentinel `'-- Select --'` | |
| Multi-select | `[]` | |
| Checkbox | `false` when required = must-be-checked | Distinct from "unset" |
| Radio | no option selected | |
| File upload | no file / failed upload | Server must re-check; client MIME is advisory |

## 4. Rollout (backward compatible)

Additive throughout — nothing is ripped out mid-flight, satisfying AC7 and req 11.

- **P1 — Foundation.** Filter + `apiClient` error mapping + message catalog. **Fixes 2.3 app-wide with zero form changes**, since every form already reads `error.response.data.message`. Highest value per unit of risk; ship alone.
- **P2 — Schema.** `ValidationSchemaService`, `@RequiredWhen`, `useValidatedForm`, extended `FormField`. No form migrated yet.
- **P3 — Pilot.** Migrate **`AssetManagement.tsx`** — it owns the dead conditional rule (2.1) and the missing LOCATION branch. Its regression suite becomes the migration template.
- **P4 — Backfill the DTOs.** Convert the 223-vs-18 skew into real `@IsNotEmpty`. **This is the only phase that can reject writes previously accepted** — see Risks and §4.3.
- **P5 — Migrate remaining forms**, one PR each, worst-gap-first (§4.1).

### 4.1 Migration order after the pilot

Worst-gap-first — the forms with the least validation today carry the most bugs.

| Order | Forms | Why |
|---|---|---|
| 1 ✅ | `IssueReturnPage.tsx` | **Done.** Bare HTML `required` attributes only — browser-native, no error text |
| 2 | `LicenseForm.tsx` | Kills the duplicate local `FormField` fork; migrates the brittle `'Other'`-vendor name-match rule |
| 3 | Admin masters (`CategoryMaster`, `PermissionMaster`, `RoleMaster`, `MasterManagement`) | Ad-hoc tier, simple + repetitive — fast once the P3 template exists |
| 4 | `ConsumableInventory/*`, `StockPage.tsx` | Ad-hoc, moderate complexity |
| 5 | `useForm` tier (`Login`, `CatalogPage`, `UserManagement`, `UserProfile`, `UserSettings`) | Already has structured rules + asterisks; lowest risk, least gain |
| 6 | **Delete `useForm.ts`** | Only once tier 5 is empty. This is what retires the §2.1 dead-rule bug class permanently |

### 4.3 The P4 backfill and its observation window

**Decision (owner):** external/automated consumers are **unknown, not absent**. Backfilled rules therefore observe for at least one production release, capturing endpoint and caller identity, and are reviewed before enforcement.

**Observation is per-property, not global.** The first cut of this used a single `VALIDATION_ENFORCE=false` switch — which would also have stopped enforcing rules that work today, making the release intended to be *safe* the one that admits bad data. Instead `@Observe` marks individual backfilled rules:

```ts
@Observe('Backfill 2026-07: already mandatory, but accepted an empty string')
@IsNotEmpty()
softwareName: string;
```

A failure on an observed property is recorded and allowed through; **every other rule rejects exactly as before**. `VALIDATION_ENFORCE_OBSERVED=true` promotes them; deleting the decorators finishes the job.

**What was backfilled (25 fields, 9 DTOs).** Deliberately one narrow class: properties that were *already mandatory* (no `@IsOptional`, so a missing value already 400s) but accepted `''` because `@IsString()` considers an empty string valid. This closes the empty-string hole without newly requiring anything — the smallest change that satisfies "no record can be saved when a mandatory field is missing". Skipped: `ChangePasswordDto` (`newPassword` already has `@MinLength(8)`; an empty `currentPassword` already fails bcrypt with a 401, and converting that to a 400 is churn on an auth path).

**Reporting.** `GET /validation/observations` (`settings.manage`) returns rules ranked by occurrence with `firstSeen`/`lastSeen` and last-known caller (user id, email, IP, user-agent). `nonUiSuspects` counts rows whose caller has no user id or a non-browser user-agent — the likely scripts and integrations. Rows aggregate on `(method, path, field, constraint)` and count, so the table stays bounded; a row per failure could be inflated indefinitely by a caller in a retry loop.

Caller identity reaches the pipe via `AsyncLocalStorage` (`RequestContextMiddleware`) — pipes receive only `ArgumentMetadata`, so without it an observation could say *what* failed but not *who* called or *which* endpoint, which is precisely what the review needs.

### 4.2 Feature flagging

**No per-module flag, and no new flag infrastructure.** The frontend has none today (the only `process.env` use is `REACT_APP_API_URL` in `apiClient.ts:3`), and building one is a project of its own. The rollout is already gated by being additive and per-form: un-migrated forms use the old path, migrated ones use the new. That is a feature flag with extra steps.

The one exception is **P4's log-only mode**, which needs a genuine runtime switch: a single backend env var (`VALIDATION_ENFORCE`, default `false` for one release). Deliberately **not** per-module — the point is to review what *would* have broken across the entire API surface before enforcing anywhere.

## 5. Test plan

- **Unit** — emptiness predicate per field type (incl. number `0`, checkbox `false`, empty multi-select); `@RequiredWhen` both branches; message catalog resolution.
- **Integration** — API-direct writes with each mandatory field omitted → 400 (**this is AC1's server half, and much of it fails today**); filter output shape; schema-vs-DTO contract test (AC5).
- **UI** — asterisk renders; submit blocked; error text per field; **explicit regression for 2.1**: `targetType=PERSON` + empty `userId` must block (asserted failing before the fix).
- **Boundary** — `0`, `''` vs whitespace, `[]`, `false`, min/max edges, oversized file.
- **Bulk** — users only; per-row failure must not silently drop the row.

## 6. Assumptions

1. **Copy/duplicate (req 7) has no implementation to validate.** No such feature exists. Design accommodates it (it's just Create with prefilled defaults); nothing to test until it's built.
2. **Bulk (req 7) means users only** — the only bulk endpoints. "Bulk Qty" in `CatalogPage.tsx:132` is a `trackMode` enum value, not a bulk op.
3. **Localization (req 10) = "localizable", not "localized". CONFIRMED by owner.** Messages use stable keys and a central catalog; adding i18next, locale files, language selection and translated content is explicitly out of scope for this story.
4. ~~`react-hook-form` is fair game to activate rather than remove.~~ **Revised during implementation.** `useValidatedForm` is schema-driven and needs no form library: rules arrive as data from the server, and the hook keeps the existing `useForm` surface so migration is mechanical. Pulling in react-hook-form would have added a dependency and a second idiom for no gain. It remains unused — a follow-up should remove it.
5. ~~The `main.ts:34-43` / `test/utils/create-test-app.ts` duplication gets unified.~~ **The named file does not exist.** The comment at `main.ts:33` points at nothing. The real duplicate is an inline `new ValidationPipe({...})` in `test/security.e2e-spec.ts:67`. `createValidationPipe()` is now the single source; the e2e spec should be pointed at it.

### Discovered during implementation

6. **class-validator 0.14.x registers every built-in decorator as `type: 'customValidation'`** and carries the identity in `name`. The design assumed `type` held `'isString'` etc. — it does not. The schema service keys off `name`, and `validation-schema.service.spec.ts` pins this shape so a version bump fails loudly rather than silently emitting empty schemas.
7. **`@RequiredWhen` must not be combined with `@IsOptional`.** `@IsOptional` skips validation whenever a value is absent — exactly when a conditional rule must fire — so it silently defeats the rule, reproducing the §2.1 bug class. `ValidationSchemaService` now throws at boot if any DTO pairs them.
8. **`@RequiredWhen` emits its own `@IsNotEmpty`.** Gating `@IsString()` alone is not enough: `''` is a valid string, so a "required" field would accept empty input. This also fixes the same latent hole in the original `@ValidateIf` code.

### Two constraints found while migrating IssueReturnPage

**Radix Select cannot be a direct FormField child.** FormField clones the id, aria attributes and className onto its child; Radix's `Select` root is a context provider with no DOM node, so those props would vanish — leaving the control unlabelled for assistive tech and unstyled in error. `components/shared/SelectField.tsx` adapts it by landing them on `SelectTrigger`. The alternative — downgrading to a native `<select>` like the asset form uses — would have changed how existing screens look. Use `SelectField` for every Radix Select from here on.

**FormField's `label` is now `ReactNode`, not `string`.** Several forms put an icon inside the label; typing it as `string` silently dropped them on migration. Widening is backward compatible — a string is a ReactNode.

**Testing note:** jsdom 16 (pinned by react-scripts) does not implement form submission, so clicking a submit button never fires `onSubmit` — verified directly with a probe. Form tests must dispatch `fireEvent.submit(form)`. A click-based test will silently pass through without ever running the handler, which looks like a working test and is not. (The former `auth.service.spec.ts` failure was a fixture omitting `isActive`; fixed at the owner's request — unrelated to this work.)

**P4 is not finished until the observation window is reviewed.** Shipping the code is step one of three: observe → review → `VALIDATION_ENFORCE_OBSERVED=true` → delete the decorators.

**One behaviour change, deliberate:** `DeployAssetDto.reason` now rejects `''`. `AssetsService.deploy()` already threw on an empty reason, so this only moves an existing guard into the DTO — no caller that succeeds today starts failing. `deploymentDate` was deliberately **left optional** server-side because the service defaults it to now and API callers rely on that; the form's requirement of it is a documented UI-only rule.

## 8. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| **P4 rejects writes the API previously accepted** — integrations or scripts may be posting partial payloads that pass today | **High.** Breaks external callers | Log-only mode first: filter records what *would* have failed for one release; review before enforcing. This is the main reason P4 is late in the order |
| class-validator internal metadata API shifts on upgrade | Medium | Pin + contract test (AC5) |
| Schema endpoint drifts from DTO | Medium | Impossible by construction — reflected, not re-declared |
| `@RequiredWhen` can't express a needed rule | Medium | Documented escape hatch to paired cross-field validators |
| Migration regresses a working form | Medium | One PR per form; existing suite green at each step |
| Scope: 14+ forms, 17 DTOs | Medium | Phased; P1 delivers value standalone |
